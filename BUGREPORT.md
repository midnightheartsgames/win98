# Отчёты об ошибках: Win 98 (F10) и HSR 98 (F9)

План от 2026-10-27. Реализация идёт по этапам, один этап за шаг, после каждого этапа нужно одобрение.

## Зачем

1. Игрок нажимает одну клавишу, пишет одну строку и отправляет. На всё уходит меньше 30 секунд.
2. Отчёт сам собирает то, что игрок не опишет словами: скриншот, открытые окна, где именно находится игрок, ошибки консоли, последние действия, по желанию сохранение.
3. Разработчик получает отчёты в одну папку `bugreports/`. Claude читает оттуда `report.md` и `shot.png`, воспроизводит баг на точном состоянии и правит код.
4. Свои баги разработчик отправляет той же клавишей. Тогда не нужно описывать Claude, что открыто и где.

## Что уже есть в проекте и что из этого используем

| Факт | Следствие для плана |
| --- | --- |
| Все приложения и игры работают в одном документе `index.html`, без iframe. | Один перехватчик клавиш на `window` в фазе capture видит F10 из любой игры. |
| `electron/main.js` без preload. В exe уже работает `server.js` на 127.0.0.1:39898. | Точный скриншот в exe даёт `webContents.capturePage()` через новый preload. |
| В браузере нет API для скриншота страницы без запроса разрешения. | Для браузера нужен свой сборщик кадра (DOM + canvas). |
| HSR 98 рисует всё в один 2D canvas (`hsr-ui.js:63`). | Скриншот HSR = `canvas.toDataURL()`, без потерь и без сборщика. |
| HSR занимает F7 и F8 (`hsr-ui.js:148-149`). F9 в HSR свободна. | F9 в HSR без конфликтов. |
| F10 занята: BIOS Setup (сохранить и выйти), Fallout (выход), Другая война (помощь). F9 занята как быстрая загрузка в многих играх, но это не важно: F9 работает только внутри HSR. | Для F10 нужны исключения и запасная комбинация Ctrl+F10. |
| `backup-catalog.js` знает ключи сохранений каждого приложения. `BackupStore.snapshot` умеет их выгружать. | Сохранение активной игры прикладываем через каталог, без нового кода для каждой игры. |
| HSR standalone (`tools/hsr98-standalone.cjs`) берёт список скриптов из `hsr98.html`. APK уже умеет `Sr98Android.saveFile`. | Общий модуль подключаем в `hsr98.html`. Сохранение отчёта в файл на Android работает через уже готовый мост. |
| `AndroidManifest.xml` без `android.permission.INTERNET`. | В APK надо добавить разрешение, иначе отправка не пройдёт. |
| pennygachi.men работает на мини-ПК разработчика, перед ним стоит Cloudflare. | Приёмный сервер ставим на тот же мини-ПК, на путь `/api/bugs` того же домена. |
| В HSR нет константы версии, `v1.6` записана строкой в `Hsr98.BRAND`. | Добавить `Hsr98.VERSION`, из неё строить строки бренда и `VERSION_NAME` APK. |

## Общая схема

```
игра / система
  F10 или F9
    1. снимок кадра (до открытия окна отчёта)
    2. снимок контекста (окна, место, журнал, действия)
    3. окно отчёта: игрок пишет текст, проверяет, что уйдёт
    4. отправка
         ├─ dev: server.js пишет в I:\win98-clone\bugreports\<id>\
         └─ игроки: https://pennygachi.men/api/bugs (приёмник на мини-ПК)
               уведомление с кадром в Telegram
               нет связи → очередь в IndexedDB, повтор при следующем запуске
               или «Сохранить в файл» → BR-....bugreport.json

разработчик
  node tools/bugs.cjs pull     → скачивает новые отчёты в bugreports/
  node tools/bugs.cjs serve    → веб-приёмка на localhost:8099
  Claude читает bugreports/<id>/report.md и shot.png
  node tools/bugs.cjs repro <id> → игра на отдельном origin с состоянием из отчёта
```

## Формат отчёта

Один формат для системы и для HSR. Поле `source` говорит, кто собрал отчёт.

Идентификатор: `BR-ГГММДД-XXXX`, где XXXX это 4 случайных символа Crockford base32. Его создаёт клиент, поэтому номер известен сразу, даже без связи. Игрок может назвать номер, разработчик может сказать Claude «разбери BR-261027-7K3Q».

Пакет для отправки (решение этапа 1, вместо multipart): один JSON, тот же формат, что у файла «Сохранить в файл». Так у клиента, локального приёма, приёмника на мини-ПК и команды `import` один разборщик.

```json
{ "format": "win98-bugreport-file", "v": 1, "report": { "format": "win98-bugreport", "v": 1, "id": "BR-261027-7K3Q" }, "files": { "shot.png": "<base64>", "save.json.gz": "<base64>" } }
```

Имена файлов только из списка ниже, номер проверяется шаблоном `^BR-\d{6}-[0-9A-HJKMNP-TV-Z]{4}$`, повтор номера даёт 409.

Файлы одного отчёта:

| Файл | Содержимое | Предел |
| --- | --- | --- |
| `report.json` | всё, кроме картинок и сохранения | 300 КБ |
| `shot.png` или `shot.jpg` | кадр; закрытые игроком области уже залиты чёрным | 1,5 МБ |
| `shot-marked.png` | тот же кадр с красными рамками игрока, если рамки есть | 1,5 МБ |
| `shot-window.png` | активное окно в исходном разрешении экрана; только если общий кадр пришлось уменьшить до 1600 px (большой монитор, exe) | 1,5 МБ |
| `save.json.gz` | сохранение активной игры, только если игрок не снял галочку | 1 МБ после gzip (`CompressionStream`) |
| `report.md` | создаёт приёмка, не клиент: человекочитаемая сводка для Claude | — |

## Сбор контекста

### Трассировка с первой секунды

`js/bugreport-core.js` подключается первым скриптом в `index.html` и `hsr98.html`. Он должен работать до загрузки остальных скриптов, иначе ошибки загрузки не попадут в отчёт.

- `console.error` и `console.warn`: последние 100 записей. `console.log`: последние 100 записей в отдельном кольце (в играх много отладочного вывода).
- `window` `error` и `unhandledrejection`: сообщение, файл, строка, стек. Одинаковые ошибки склеиваются со счётчиком.
- Ошибки загрузки ресурсов (`error` в фазе capture на `img`, `script`, `audio`, `link`): путь к файлу. Так видны пропавшие картинки и музыка.
- Действия (`trail`), последние 150 или 5 минут:
  - нажатия клавиш: только `code` и окно. Если фокус в `input`, `textarea` или `contenteditable`, пишется одна запись `typing`, без символов. Поля паролей не пишутся никогда;
  - клики: окно, тег, класс, текст кнопки до 30 символов;
  - открытие, закрытие, фокус, сворачивание окон (обёртка методов `winManager`);
  - переходы IE и Netscape, запуск игр из `gameManager`;
  - события, которые приложение само сообщает через `BugTrace.note(msg)`. HSR сообщает смену режима, начало и конец боя, запуск сценки.
- FPS за последние 2 секунды и `performance.memory.usedJSHeapSize`, если браузер его даёт.

### Место в системе (F10)

`js/apps/bugreport-where.js`: одна таблица, ключ = id окна, значение = функция, которая читает уже существующие глобальные объекты. Сами приложения при этом не меняются.

| Окно | Строка «где» |
| --- | --- |
| нет активного окна | Рабочий стол, открытые меню |
| Проводник | путь в VFS |
| IE, Netscape | адрес страницы |
| Steam | вкладка и открытая игра |
| Блокнот, WordPad | имя файла (текст файла не отправляется) |
| Игра из каталога | название, id, установлена ли, с Steam или с CD |
| HSR 98 | строка из `hsrui.bugInfo()` (см. ниже) |
| другое | заголовок окна |

Для игр без своей функции дополнительно собирается: число canvas и их размеры, WebGL-рендерер, захвачен ли указатель, полноэкранный ли режим, состояние AudioContext из `SystemMixer`.

Подробные адаптеры для других игр добавляются потом, когда по игре придёт первый отчёт, где их не хватило. Заранее их не пишем.

### Место в HSR (F9 и F10)

`js/apps/hsr98/hsr-bug.js` добавляет `hsrui.bugInfo()`. Он возвращает строку `where` и объект `state`:

- издание (система, web, APK), `Hsr98.VERSION`, номер слота, время игры;
- `mode` и стек экранов (`screens`) по именам. Экранам без имени добавить поле `name`, иначе в отчёте будут номера без смысла;
- поле: id и название карты, координаты и направление игрока, NPC и объекты в радиусе 3 клеток, активная сценка и шаг сценки;
- бой: id боя, волна, ход, отряд (id, уровень, HP, энергия), враги (id, HP, слабости), очередь действий, последние 20 строк журнала боя;
- сюжет: текущий шаг основной миссии и активные задания;
- валюты: нефрит, кредиты, энергия освоения, уровень освоения, гарант молитв;
- подрежимы, только если активны: Виртуальная вселенная, Валютные войны, Рубеж Экспресса (номер забега, волна, герои);
- флаг `cheats`: нажимались ли F7 или F8 в этом сохранении. Для этого в состояние сохранения добавляется счётчик `dbgUsed`. Отчёты с читами в приёмке помечены.

Сохранение для HSR прикладывается по умолчанию: текущее состояние из памяти (с несохранённым прогрессом) и блок слота. Без него большинство багов HSR не воспроизвести.

### Сохранение в системе

Галочка «Приложить сохранение (Название игры, 240 КБ)» появляется, если для активного окна в `backup-catalog.js` есть компонент. Данные берёт `BackupStore.snapshot` только для этого компонента. Для системных окон (Проводник, IE) галочки нет. По умолчанию галочка снята, кроме HSR.

## Скриншот

Кадр снимается сразу по нажатию клавиши, до открытия окна отчёта. Окно отчёта на снимок не попадает.

| Где запущено | Способ | Качество |
| --- | --- | --- |
| exe (Electron) | `electron/preload.js` даёт `win98Native.capture()`. В `main.js` обработчик `ipcMain.handle('capture')` вызывает `webContents.capturePage()`. | точный кадр окна |
| HSR (любое издание) | копия основного canvas игры | точный кадр |
| браузер, система | свой сборщик: клон DOM с вычисленными стилями в SVG `foreignObject`, каждый canvas заменён его `toDataURL()`, картинки переведены в data URL | почти точный, 200–400 мс |
| сборщик не справился | отчёт уходит без кадра, в `attach.shot` записана причина | — |

WebGL canvas без `preserveDrawingBuffer` даёт пустую картинку, если читать его не в том кадре. Поэтому сборщик читает canvas внутри `requestAnimationFrame`, который регистрируется после кадра игры: в этот момент буфер ещё не очищен.

Формат: PNG, если файл меньше 1,5 МБ, иначе JPEG с качеством 0,88 (тогда расширение `.jpg`). Общий кадр не шире 1600 px. Если экран шире (в exe на мониторе 3840 px кадр приходит 3840×2055), отдельно сохраняется `shot-window` — активное окно без уменьшения, чтобы мелкий текст читался.

Инструменты в окне отчёта:

- «Пометить»: игрок рисует красные рамки вокруг места бага. Получается `shot-marked.png`, исходный кадр не меняется.
- «Скрыть»: чёрные прямоугольники. Они вписываются в сам кадр до отправки, исходник без них не уходит.
- «Переснять»: окно отчёта прячется, через 2 кадра снимок повторяется, окно возвращается. Нужно, если баг виден только на долю секунды позже.

## Окно отчёта в системе (F10)

Назначение окна: записать один баг быстро и показать игроку, что именно уйдёт разработчику. Окно не похоже на остальные диалоги системы по раскладке: главное в нём кадр и одно поле, остальное свёрнуто.

Вызов:

- F10 из любого места после загрузки рабочего стола;
- Ctrl+F10 всегда, в том числе в играх, где F10 занята;
- «Пуск > Программы > Стандартные > Служебные > Сообщение об ошибке», Выполнить `bugreport`, файл `C:\WINDOWS\BUGREPORT.EXE`.

F10 не перехватывается, когда: идёт POST, BIOS Setup или загрузка; активна Fallout или Другая война (у них своя F10). Список исключений лежит в одном массиве в `bugreport.js`. При первом таком случае в строке состояния окна игры ничего не меняется, но в справке F1 написано про Ctrl+F10.

Раскладка (окно 560×470, модальное, по центру):

```
┌ Сообщение об ошибке ─────────────────────────────── ? × ┐
│ ┌──────────────┐  Где: Honkai: Star Rail 98 > Ярило-VI  │
│ │   кадр       │       > Белобог (x 312, y 140)          │
│ │  240×180     │                                         │
│ │              │  Что случилось? *                       │
│ └──────────────┘  [__________________________________]   │
│ [Пометить] [Скрыть] [Переснять]                          │
│                                                          │
│ Подробности (что делали, что ожидали):                   │
│ [                                                    ]   │
│ [                                                    ]   │
│ Тип: [Не работает ▼]      Повторяется: [Всегда     ▼]   │
│                                                          │
│ ▸ Что будет отправлено (5)                               │
│ Как с вами связаться (необязательно): [______________]   │
│                                                          │
│ [Мои отчёты (3)] [В файл...]        [Отправить] [Отмена] │
└──────────────────────────────────────────────────────────┘
```

Кнопка «Мои отчёты (3)» внизу слева открывает отдельное окно со списком отправленных отчётов (см. «Мои отчёты» ниже). Число в скобках выделено жирным, если с прошлого просмотра у какого-то отчёта сменился статус.

«Что будет отправлено» раскрывается в список галочек: кадр, сведения о системе и окнах (нельзя снять), журнал ошибок, последние действия, сохранение. Рядом кнопка «Показать данные», она открывает точный `report.json` в Блокноте только для чтения.

Поведение:

- фокус сразу в поле «Что случилось?»;
- «Отправить» неактивна, пока поле пустое. Ctrl+Enter отправляет;
- Esc и «Отмена»: если текст уже введён, система спрашивает «Отменить отчёт?»;
- окно одно: повторная F10 при открытом окне только активирует его;
- игра под окном теряет фокус. Игры, которые ставят паузу при потере фокуса, встают на паузу. Для остальных паузу не добавляем в этом плане;
- при первом открытии одна строка над кнопками: «Отчёт получит разработчик на pennygachi.men. Пароли и набранный текст не отправляются.»

Состояния:

| Состояние | Что видит игрок | Выход |
| --- | --- | --- |
| Снимок | курсор «песочные часы» до 0,5 с | окно открыто |
| Ввод | окно | Отправить / Сохранить / Отмена |
| Отправка | полоса прогресса, кнопки неактивны | успех или ошибка |
| Отправлено | «Отчёт BR-261027-7K3Q отправлен. Спасибо!» и кнопка «Копировать номер» | ОК закрывает |
| Нет связи | «Сервер не ответил. Отчёт сохранён и уйдёт сам при следующем запуске.» и кнопка «Сохранить в файл» | ОК закрывает, отчёт в очереди |
| Отказ сервера (лимит, размер) | текст причины и «Сохранить в файл» | ОК |

Тексты окна на RU и EN через `L()` из i18n. Названия по правилу проекта: Microslop, Win.

## Окно отчёта в HSR (F9)

Окно рисуется в стиле интерфейса HSR, как экран из стека `screens`. Оно не повторяет раскладку системного окна: в HSR управление идёт стрелками, Enter, Esc и касаниями, поэтому поля идут одним столбцом и выбираются по одному.

Вызов: F9 в любом режиме, кроме экрана заставки при загрузке. В standalone и APK на панели касаний рядом с F7 и F8 появляется кнопка «Баг». В системе внутри окна HSR работают обе клавиши: F9 открывает окно HSR, F10 открывает системное окно, и в него тоже попадает `hsrui.bugInfo()`.

Порядок экрана:

1. Кадр в половинном размере и строка «где» под ним.
2. «Что случилось?»: при выборе поля поверх canvas появляется настоящий `textarea`. Он нужен для экранной клавиатуры на телефоне и для ввода кириллицы.
3. Тип: переключатель Q/E или касание по ярлыку.
4. Повторяется: переключатель.
5. «Приложить сохранение»: включено.
6. «Отправить», «Сохранить в файл», «Мои отчёты».

Пока экран открыт, время в бою и в Рубеже Экспресса стоит, как в других меню HSR. Энергия освоения идёт по реальным часам, её это не касается.

«Мои отчёты» в HSR: экран со списком, устроенный как остальные списки HSR (стрелки, Enter открывает отчёт с кадром и текстом, Esc назад).

Отчёты лаунчера не воспроизводятся, по ним смотрят кадры.

## Мои отчёты (Win 98 и HSR)

Игрок видит, что отчёт дошёл и что с ним стало. Без этого второй отчёт игрок обычно уже не шлёт.

- Список хранится у игрока: номер, дата, заголовок, где, миниатюра кадра 120×90. Ключ `win98.bugs.sent` в системе и `sr98.bugs.sent` в standalone и APK. Отчёты, отправленные из HSR внутри системы, попадают в оба списка, потому что origin один.
- Статусы берутся запросом `GET /api/bugs/status?ids=...` при открытии списка и не чаще раза в 10 минут. Без связи показывается последний известный статус и строка «нет связи, статусы от 27.10 14:03».
- Статусы для игрока: «В очереди» (ещё не ушёл), «Получен», «Принят», «Исправлен в версии 1.7», «Уже известен», «Не ошибка», «Не будет исправлен». Рядом может стоять короткая заметка разработчика из `--note`.
- Win 98: окно «Мои отчёты» с таблицей (номер, заголовок, дата, статус) и панелью предпросмотра выбранного отчёта. Открывается из окна F10, из `Пуск > ... > Служебные > Мои отчёты об ошибках` и командой `bugreport /list` в «Выполнить».
- Win 98: при загрузке рабочего стола, не чаще раза в сутки, статусы проверяются в фоне. Если какой-то отчёт стал «Исправлен», в области уведомлений появляется значок, по щелчку открывается «Мои отчёты».
- HSR: на пункте «Мои отчёты» в окне F9 горит точка, если статус сменился.
- Строку из списка можно удалить у себя. На сервере отчёт от этого не удаляется.
- Наград за отчёты нет: награда даёт повод слать пустые отчёты.

## Отправка и очередь

Порядок адресов в `bugreport-core.js`:

1. Если страница открыта с `127.0.0.1` или `localhost` и `GET /api/bugs/ping` отвечает `{ "local": true }`, отчёт уходит в `server.js`.
2. Иначе `POST https://pennygachi.men/api/bugs`.
3. Ошибка сети или 5xx: отчёт целиком ложится в IndexedDB `win98_bugs`, хранилище `outbox`. При следующем запуске очередь отправляется в фоне, по одному отчёту, с паузой 5 с. Через 14 дней неотправленный отчёт удаляется.

Очередь хранится в IndexedDB, а не в localStorage: кадр весит до 1,5 МБ, а в localStorage лежат сохранения HSR, и переполнение квоты сломает сохранения.

Локальный приём в `server.js`: обработчик включается, только если рядом с `server.js` есть папка `bugreports/` или задана переменная `WIN98_BUGS_DIR`. В репозитории папка есть (в `.gitignore` и в исключениях `build-exe.mjs`), в exe у игроков её нет. Поэтому exe игроков всегда шлёт на pennygachi.men, а запуск из репозитория пишет прямо в `I:\win98-clone\bugreports\`.

«Сохранить в файл» создаёт `BR-261027-7K3Q.bugreport.json`: тот же отчёт, кадр и сохранение внутри в base64. В браузере и exe через загрузку blob, в APK через `Sr98Android.saveFile`. Такой файл приёмка принимает командой `import`.

Новые хранилища (`win98_bugs`, ключ `win98.bugs.sent` со списком своих отчётов, ключ `sr98.bugs.sent` в standalone) добавить в `backup-catalog.js` отдельным компонентом «Отчёты об ошибках» и в `tests/backup.test.js`.

## Приёмка

Приёмка состоит из двух частей: сервер принимает отчёты от игроков, локальная программа забирает их и показывает разработчику и Claude.

### Сервер на мини-ПК

Приёмник работает на том же мини-ПК, где держится pennygachi.men. Отдельный хостинг не нужен, данные остаются у разработчика.

Факты о мини-ПК (разведка 27.10.2026):

- Debian 13 (trixie), x86_64, 11 ГБ RAM, один SSD, свободно 158 ГБ. Пользователь `debianserver` в группе sudo (sudo с паролем).
- Node не установлен. Ставится из apt: `nodejs` 20.19.2, `/usr/bin/node`. npm не нужен.
- Сайт отдают два контейнера Docker: nginx-proxy-manager (порты 80 и 443) и static-site (файлы `/srv/www/site`).
- Серый IP. Входящий трафик идёт только через Cloudflare Tunnel: служба `cloudflared` на хосте, туннель настраивается в панели Cloudflare (Zero Trust > Networks > Tunnels), сейчас одно правило `pennygachi.men > http://localhost:80`. Туннель работает через VPN (`sotad.service`).
- Исходящая связь с api.telegram.org есть.
- Порт 39899 свободен.

Программа: `tools/bugs/receiver.cjs`, один файл на Node 20 без зависимостей. Слушает только `127.0.0.1:39899`.

Публикация: отдельное правило в том же Cloudflare Tunnel, NPM и Docker не трогаем. В панели туннеля в Public Hostnames добавляется `pennygachi.men`, path `^/api/bugs`, service `http://127.0.0.1:39899`. Правило ставится выше общего правила `pennygachi.men > http://localhost:80`. `cloudflared` работает на хосте и видит его 127.0.0.1, а наружу и в локальную сеть порт не открывается.

Почему не через NPM: NPM работает в контейнере, и для него `127.0.0.1` не адрес хоста. Пришлось бы слушать `172.18.0.1` и зависеть от старта Docker.

Установка на мини-ПК:

| Что | Где |
| --- | --- |
| программа | `/opt/bug-receiver/receiver.cjs` |
| служба systemd | `/etc/systemd/system/bug-receiver.service` (образец в `tools/bugs/bug-receiver.service`) |
| секреты и настройки | `/etc/bug-receiver.env`, владелец `debianserver`, права 600 (образец `tools/bugs/bug-receiver.env.example`) |
| данные | `/var/lib/bug-receiver/` (создаёт systemd через `StateDirectory=`) |

Данные не лежат в `/srv/www/site`: эту папку раздаёт сайт.

Раскладка данных та же, что в локальной папке разработчика:

```
/var/lib/bug-receiver/
  index.jsonl              одна строка на отчёт: id, дата, source, app, kind, title, status, fixedIn, note
  outbox-telegram.jsonl    уведомления, которые ещё не ушли в Telegram
  BR-261027-7K3Q/
    report.json
    shot.png
    shot-marked.png
    save.json.gz
```

Поэтому `pull` просто копирует папки, а разбор одинаковый для своих и чужих отчётов.

- Файлы отчёта хранятся 90 дней с даты приёма, потом приёмник удаляет папку. Проверка раз в сутки внутри самого приёмника.
- Строка в `index.jsonl` со статусом остаётся и после удаления файлов, она весит меньше 1 КБ. Так «Мои отчёты» показывают статус и для старых отчётов.
- Лимит по IP держится в памяти приёмника: до 10 отчётов в час. IP не пишется на диск. Запросы приходят от `cloudflared` с 127.0.0.1, поэтому настоящий IP берётся из `CF-Connecting-IP`.
- Ответы `/api/bugs/*` идут с `Cache-Control: no-store`. Дополнительно в Cloudflare ставится Cache Rule «Bypass cache» для пути `/api/bugs*`.
- Диск у мини-ПК один, на нём MySQL и игровые серверы. Поэтому два предела: все данные приёмника не больше `BUGS_MAX_GB` (по умолчанию 5 ГБ) и свободно на диске не меньше 2 ГБ. При нарушении приёмник отвечает 507 и пишет в Telegram одно предупреждение в сутки.
- Туннель и Telegram зависят от VPN. Если VPN упал, клиенты держат отчёты в своей очереди, а приёмник держит неотправленные уведомления в `outbox-telegram.jsonl` и повторяет их каждые 5 минут до успеха.
- WAF и Bot Fight Mode Cloudflare могут не пропускать POST. На этапе 4 это проверяется отправкой из exe, из браузера и из APK-WebView.

Настройки в `/etc/bug-receiver.env`:

```
BUGS_HOST=127.0.0.1
BUGS_PORT=39899
BUGS_TOKEN=<64 hex, node -e "console.log(require('crypto').randomBytes(32).toString('hex'))">
BUGS_KEEP_DAYS=90
BUGS_MAX_GB=5
TELEGRAM_BOT_TOKEN=<токен от @BotFather>
TELEGRAM_CHAT_ID=<id чата, печатает receiver.cjs find-chat>
```

Команды приёмника:

| Команда | Что делает |
| --- | --- |
| `node receiver.cjs --env /etc/bug-receiver.env` | запуск сервера (так его запускает служба, только без `--env`: служба читает файл сама) |
| `node receiver.cjs find-chat --env /etc/bug-receiver.env` | печатает чаты, которые писали боту, чтобы узнать `TELEGRAM_CHAT_ID` |
| `node receiver.cjs test-telegram --env /etc/bug-receiver.env` | отправляет пробное сообщение в чат |

API:

| Метод | Доступ | Назначение |
| --- | --- | --- |
| `GET /api/bugs/ping` | открыт | `{ ok: true }`, проверка связи из клиента |
| `POST /api/bugs` | открыт, CORS `*` | JSON-пакет `win98-bugreport-file` (см. «Пакет для отправки»). Проверка схемы и типов файлов, размер до 10 МБ, лимит по IP, отказ при повторе номера. Ответ `{ ok, id }`. |
| `GET /api/bugs/status?ids=a,b` | открыт | только статус, версия исправления и заметка для этих номеров, для «Мои отчёты». До 50 номеров за запрос. |
| `GET /api/bugs?since=<iso>` | `Authorization: Bearer <token>` | список отчётов из `index.jsonl` |
| `GET /api/bugs/<id>/<file>` | токен | файл отчёта, всегда как `attachment` |
| `POST /api/bugs/<id>/status` | токен | `{ status, fixedIn, note, dup }` |

Запрос с `Content-Type: application/json` вызывает предварительный запрос CORS, приёмник отвечает на `OPTIONS` кодом 204 с `Access-Control-Allow-Origin: *`. Поэтому отправка работает с любого origin: `http://127.0.0.1:39898` (exe), `http://localhost:8080`, `https://pennygachi.men`, `https://appassets.androidplatform.net` (APK), `null` (file://).

Токен на машине разработчика: переменная `WIN98_BUGS_TOKEN` или файл `%USERPROFILE%\.win98-bugs.json`. В репозиторий токен не попадает.

### Telegram

Бот разработчика (токен в `/etc/bug-receiver.env`) пишет в один чат, личный или группу.

- После приёма отчёта бот отправляет `sendPhoto`: кадр (с рамками игрока, если они есть) и подпись до 1024 символов:

```
🐞 BR-261027-7K3Q · HSR 98 · exe · Не работает · всегда
Пропал диалог с Броней после боя
Где: Ярило-VI > Белобог, Административный район (x 312, y 140)
Ошибки: TypeError ... (hsr-cine.js:211) ×3
Сборка 63d95ed · сохранение приложено
```

- Под сообщением кнопки: «Принять», «Не ошибка», «Уже известен». Нажатие меняет статус на сервере, и игрок увидит это в «Моих отчётах». Кнопки работают через опрос `getUpdates` из приёмника, поэтому публичный адрес для Telegram не нужен. Нажатия принимаются только из чата `chatId`.
- Отчёт с флагом «читы» помечается в подписи строкой «⚠ F7/F8 использовались». В HSR 98 этот же флаг ставит выдача секретных пропусков. Если в сохранении есть тестовые героини секретного прыжка, в сводке отчёта стоит `[закрытый тест: ...]`, а в `state.lab` их список.
- Если Telegram недоступен, отчёт всё равно сохраняется, уведомление ждёт в `outbox-telegram.jsonl` и повторяется каждые 5 минут.
- Команды боту: `/new` (сколько новых и 5 последних заголовков), `/get BR-...` (подпись и кадр ещё раз).

### Локальная программа `tools/bugs.cjs`

Все отчёты, свои и чужие, оказываются в одной папке `bugreports/<id>/`. Это единственное место, откуда Claude их читает.

| Команда | Что делает |
| --- | --- |
| `pull` | копирует с мини-ПК новые папки отчётов и свежие статусы, пишет `report.md`. На сервере ничего не удаляет: там статусы для «Моих отчётов». |
| `import <файл>` | разбирает `.bugreport.json` в папку |
| `list [--status new] [--app hsr98] [--kind crash]` | таблица в консоли |
| `last` | путь к самому новому отчёту |
| `show <id>` | печатает `report.md` |
| `status <id> <new\|accepted\|fixed\|duplicate\|notabug\|wontfix> [--in 1.7] [--note "..."] [--dup BR-...]` | меняет статус локально и на сервере |
| `serve` | веб-приёмка на http://localhost:8099 |
| `repro <id>` | запускает игру с состоянием из отчёта (см. ниже) |

После любой команды, которая меняет данные, обновляется `bugreports/INDEX.md`: номер, дата, источник, приложение, тип, статус, заголовок, пометка «читы».

  at hsr-cine.js:211:17 ...

...

Строка про HEAD считается командой `git log <commit>..HEAD --name-only`: сразу видно, не исправлен ли баг уже.

### Веб-приёмка (`serve`)

Назначение: быстро разобрать пачку отчётов. Экран один: слева список, справа выбранный отчёт.

- Список: миниатюра кадра, заголовок, приложение, тип, возраст, статус. Фильтры по статусу, приложению, типу, флагу «читы». Новые сверху.
- Отчёт: кадр во всю ширину (переключатель «с рамками / без»), «где», текст игрока, ошибки, действия, состояние, окна.
- Кнопки: «Принять», «Не баг», «Дубликат...» (поиск по номеру), «Исправлен в...», «Копировать для Claude», «Воспроизвести».
- «Копировать для Claude» кладёт в буфер строку: `Разбери баг BR-261027-7K3Q (bugreports/BR-261027-7K3Q/report.md, кадр shot.png).`
- Весь текст игроков выводится через экранирование, HTML из отчётов не исполняется.

Приёмка находится в `tools/`, поэтому не попадает в exe и на сайт.

### Воспроизведение (`repro`)

Состояние из отчёта нельзя загружать в основной профиль: это перезапишет сохранения разработчика. Поэтому `repro` поднимает `server.js` на отдельном порту 8091. У отдельного порта свой origin и своё localStorage.

- HSR: открывается `http://127.0.0.1:8091/hsr98.html?bug=<id>`. Загрузочный код в `hsr98.html` при параметре `bug` берёт `save.json.gz` через `/api/bugs/local/<id>/save` и загружает состояние в память.
- Система: компонент сохранения из отчёта записывается через `BackupStore` в профиль порта 8091, открывается `index.html?bug=<id>`, после загрузки запускается то же приложение.
- Партия за столом Рубежа Экспресса: живое сохранение содержит поле `table`: зерно, сложность, место, номера хода и такта, хэш состояния, `HD.SIM` и журнал непустых ходов. Имён и UID других игроков там нет. `ui.bugLoad` пересчитывает партию до этого такта и открывает экран обороны с места отправителя; дальше арена стоит, ходов больше нет. В `repro.log` появляется `table: { tick, hash, expected, match, sameArena }`. Хэш разошёлся при `sameArena: true`: настоящее расхождение, его и надо разбирать. При `false` арена изменилась после сборки отчёта.
- `repro <id> --headless` делает то же в headless Edge через CDP (как в остальных инструментах проекта) и сохраняет `bugreports/<id>/repro.png`. Claude сравнивает его с `shot.png`.

## Как Claude работает с отчётом

Этот раздел после реализации переносится в `AGENTS.md`.

1. Разработчик пишет: «разбери BR-261027-7K3Q», «разбери последний баг» или «разбери новые баги».
2. Claude выполняет `node tools/bugs.cjs pull`, затем читает `bugreports/<id>/report.md` и смотрит `shot.png` (и `shot-marked.png`, если есть).
3. Если в `report.md` указаны файлы, изменённые после сборки, Claude сначала проверяет, не исправлен ли баг уже.
4. Claude воспроизводит баг: `node tools/bugs.cjs repro <id> --headless`, при необходимости шаги из `trail`.
5. Исправление идёт по обычным правилам проекта, с тестом на этот случай, если тест возможен.
6. `node tools/bugs.cjs status <id> fixed --in <версия> --note "<коротко что исправлено>"`.
7. Отчёты-дубликаты помечаются `duplicate --dup <id>`, отчёты с читами без воспроизведения помечаются `notabug` только после проверки.

## Безопасность и приватность

- Окно показывает, что уйдёт. «Показать данные» открывает точный JSON.
- Набранный текст, поля паролей и содержимое документов в отчёт не попадают. Кадр показывает только окно игры или системы, не рабочий стол компьютера игрока.
- Контакт необязателен.
- Сервер не хранит IP. Хэш IP с суточной солью нужен только для лимита.
- Файлы отдаются только с токеном и только как вложения.
- Файлы отчётов на мини-ПК живут 90 дней. После этого остаётся только строка статуса без текста игрока и без кадра.
- `bugreports/` в `.gitignore`: там данные игроков, в git они не идут.
